# D200 Deck

App para Windows que substitui o Ulanzi Studio no Ulanzi D200 (VID 2207, PID 0019), com teclas dinâmicas: regras por app ou site trocam só as teclas que sobrescrevem, no modo "aberto" ou "foco", e as teclas voltam ao layout padrão quando a regra deixa de valer.

## Decisões
- Roda nativo no Windows, **sem Docker**: USB HID, API Win32 de janelas e o Edge não existem num container. Exceção aprovada pelo usuário em 2026-10-07.
- Stack: Rust (driver e motor de regras), Tauri 2 + TypeScript (interface), extensão Manifest V3 para o Edge (sites).
- Protótipo da interface: https://claude.ai/artifact/H6LxuTWJd7RfxFkWPU4y1L
- Código em inglês; textos da interface em português.

## Fluxo de mudanças
Toda mudança, até de documentação, segue este fluxo: a `main` só aceita PR com o job "Testes" verde (ver "Versões e atualizações").
1. Partir da `main` atualizada (`git switch main && git pull --ff-only`) e criar uma branch em minúsculo: `feature/…`, `fix/…`, `refactor/…`, `docs/…` ou `ci/…`.
2. Implementar com testes. Antes do commit, rodar `cargo test -p d200 -p deck-engine` e `npm run check` (em `app`), mais `cargo check -p d200-deck` se o app Tauri mudou e `cargo check -p d200 -p deck-engine --bins` se uma ferramenta (`probe`, `deckd`, `try-*`) mudou: elas não têm testes, e o `cargo test` não as compila (`test = false`). O Rust fica em `%USERPROFILE%\.cargo\bin`.
3. Atualizar este arquivo e o `README.md` quando a mudança alterar comportamento, comandos, decisões ou armadilhas.
4. Commit em inglês, com a mensagem aprovada pelo usuário antes de rodar.
5. `git push -u origin HEAD:refs/heads/<branch>` (nome em minúsculo explícito) e `gh pr create --base main`, com a descrição (Summary, Changes, Testing) aprovada antes.
6. Acompanhar o "Testes" do PR (`gh run watch <id> --exit-status`) e, se falhar, corrigir na mesma branch. O usuário faz o merge, e a branch remota some sozinha. Depois: `git switch main && git pull --ff-only && git fetch --prune && git branch -d <branch>`.
7. Para lançar a mudança: num PR, subir a versão e escrever a seção dela no `CHANGELOG.md` (`## X.Y.Z — data`, em português, para quem usa o app, com o texto aprovado pelo usuário). Depois do merge, criar a tag e publicar o release como descrito em "Versões e atualizações".

## Estrutura
- `crates/d200/` — driver do protocolo (`protocol.rs`: pacotes; `layout.rs`: zip de layout; `device.rs`: acesso HID).
- `crates/d200/src/bin/probe.rs` — ferramenta de validação da Fase 0.
- `crates/engine/` — motor reaproveitado pelo app Tauri: `config.rs` (JSON em `%APPDATA%\D200Deck\config.json`, teclas numeradas de 1 a 14), `icons.rs` (ícones de traço do protótipo via resvg, ou PNG do usuário), `actions.rs` (atalho, abrir, comando, texto, mídia), `runtime/` (o laço do aparelho: `mod.rs` com conexão, keep-alive de 1 s, contexto, regras, recarga da config e reconexão; sem acesso ao USB (o `HidApi::new` falhou), o motor segue sem o aparelho e tenta de novo a cada 2 s, com o motivo no `Status` (`device_error`) e "Sem acesso ao USB" na janela e na bandeja, onde antes a thread do motor terminava e nada mais funcionava; `keys.rs` com o que cada tecla mostra e faz, pastas e as imagens enviadas só quando mudam; `visor.rs` com o visor, toque e segurar; `status.rs` com o `Status` e a `Activity` que o app recebe), `draw.rs` (as etapas de desenho que teclas, ícones e visor compartilham: SVG para pixels com `svg_options`, PNG, imagem centralizada numa área e cor #RRGGBB), `files.rs` (`write_atomic`: grava ao lado e renomeia por cima, com um nome temporário único por escrita; usado pela config e pelo cache do Iconify), `logging.rs` (log no stderr e em `%APPDATA%\D200Deck\d200deck.log`, que recomeça ao passar de 2 MB, também com o app aberto, guardando o anterior em `d200deck.old.log`; panics de qualquer thread também vão para o log). O app instalado não tem console: sem o arquivo, avisos e quedas do motor se perdiam.
- `crates/engine/src/bin/deckd.rs` — o app sem interface.
- `crates/engine/src/rules.rs` — quais regras valem e o que cada tecla mostra (lógica pura, testável). `context.rs` — o lado Windows: janela da frente por evento (`SetWinEventHook`), processos a cada 1 s (só os que regras "aberto" observam) e trazer um app para a frente.
- `crates/engine/src/browser.rs` — WebSocket em `127.0.0.1:47820` para a extensão. Só aceita o Origin exato da nossa extensão (`chrome-extension://` + `EXTENSION_ID`, o formato que o Edge manda, conferido em 2026-10-10): páginas da web e outras extensões são recusadas. E a conexão precisa vir do Edge (`msedge.exe`, o processo de rede dele) rodando com o mesmo usuário do Windows que o app: antes do handshake, o app acha o processo do outro lado pela tabela TCP do Windows (`GetExtendedTcpTable`) e compara o usuário (SID). Fora do navegador o Origin é só texto, e o `127.0.0.1` é de todos os usuários do PC: sem isso, qualquer programa mandando o Origin certo era aceito e, como a conexão mais nova assume, tirava da extensão o canal de pedidos ("trazer a aba", ícone do site). Um antivírus que intercepte conexões locais faria a extensão ser recusada; o log diz de qual processo veio. Mensagens de até 1 MiB, handshake em até 5 s, no máximo 4 conexões.
- `app/` — o app Tauri 2. `app/src/` é o frontend em Svelte 5 + TypeScript (`lib/types.ts` espelha o `runtime::Status`). `app/src-tauri/src/main.rs` sobe o motor (`runtime::spawn`), repassa cada `Status` para a janela (evento `status`) e para a bandeja (a bandeja vai por `run_on_main_thread`, sem esperar: cada mudança no menu espera a thread principal, e os callbacks do `runtime::spawn` rodam na thread que lê as teclas do aparelho; quando só o visor muda, a janela recebe só ele, evento `screen`, uns 13 KB em vez dos ~110 KB do `Status` com a imagem de cada tecla), e expõe os comandos `get_status`, `set_paused`, `resend`, `simulate` e `open_config`. Os comandos devolvem `CmdResult` (qualquer erro chega à janela como texto, no formato `{e:#}`); desenho, downloads e disco passam por `blocking()`, numa thread de trabalho. `get_config` e `save_config` ficam síncronos de propósito: na thread principal rodam um de cada vez, na ordem das chamadas, e um salvamento mais velho não termina depois de um mais novo. `tray.rs` é o menu da bandeja. Fechar a janela destrói o WebView e o motor continua na bandeja; só "Sair" encerra. O início automático passa `--hidden` (abre só na bandeja).
- Editores (Fase 5): `LayerEditor.svelte` edita o layout padrão e cada regra (teclas herdadas tracejadas, sobrescritas com borda âmbar), `KeyEditor.svelte` edita uma tecla, `NewRule.svelte` cria regras e `Settings.svelte` cuida de brilho, visor e estilo do texto. A classe `ConfigEditing` (`lib/editing.svelte.ts`) carrega a config, salva sozinha 350 ms depois da última mudança via `save_config`, que valida, grava de forma atômica e manda o motor recarregar (`Command::Reload`). Nada inválido chega ao arquivo; se o `config.json` mudar à mão, a revisão no `Status` faz o app recarregar. Para separar o próprio salvamento de uma edição à mão, o app compara o arquivo com o que o `save_config` devolveu (a config como foi gravada), e não pelo relógio: o motor leva de 1 a 1,5 s para anunciar a recarga (redesenha todas as teclas), e uma regra de tempo apagava o histórico de desfazer. PNGs escolhidos são copiados para `%APPDATA%\D200Deck\icons`.
- Gravar atalho usa o `keydown` da janela (`app/src/lib/hotkey.ts`). Combinações com Win não chegam à janela e são digitadas no campo. Um gancho `WH_KEYBOARD_LL` foi testado e também não capturou o Win+G nesta máquina, por isso foi descartado.
- `extension-edge/` — extensão Manifest V3 (permissões `tabs`, `alarms` e `favicon`), carregada em `edge://extensions` → Modo de desenvolvedor → Carregar sem pacote. Depois de editar, clicar em recarregar na extensão. A porta está fixa nos dois lados (`PORT`). A `key` do `manifest.json` fixa o ID (`jfahhgamoiaijnagckhknnanoobeaiko`), venha a pasta de onde vier; trocar a `key` troca o ID, e o `browser::EXTENSION_ID` precisa acompanhar (um teste compara os dois). A chave privada não existe: só serviria para empacotar um `.crx`. Os handlers do socket guardam o próprio socket, para um fechamento atrasado não derrubar o novo.

## Regras de app (Fase 2)
- Formato: `{ "name", "when": { "process": "Discord.exe" }, "mode": "open" | "focus", "enabled", "keys": { ... } }`. O nome do processo é comparado sem diferenciar maiúsculas, e `.exe` é opcional.
- **Nome da regra é único:** o motor acha a pasta aberta e os toggles pelo nome, e a janela acha no `Status` se cada regra está valendo também pelo nome (`ruleActive` em `types.ts`): a lista do `Status` é a config salva, que fica para trás da janela até o motor recarregar, e pela posição uma regra recém-arrastada ou apagada mostrava o estado de outra. O `validate` recusa repetidos (o salvamento pela interface mostra o erro), o editor gera nomes livres ao duplicar e criar (`freeRuleName` em `types.ts`: "X (2)") e avisa ao renomear para um nome que já existe, e o `Config::load` renomeia as repetidas de configs antigas antes de validar ("X" → "X (2)"; sem nome → "regra N").
- Camadas: padrão → regras "open" → regras "focus", cada grupo na ordem da lista. Foco ganha de aberto; no mesmo modo, a regra mais abaixo ganha.
- As regras ativas precisam ficar iguais por 200 ms antes de as teclas mudarem (Alt+Tab não pisca).
- `"front": true` numa tecla de regra traz o app para a frente (`AttachThreadInput`; um toque de Alt é o plano B), executa a ação e devolve o foco.
- Limitação conhecida: apps UWP (Calculadora, Configurações) aparecem como `ApplicationFrameHost.exe` na janela da frente.

## Teclas e visor (depois da Fase 5)
- **O texto das teclas é desenhado pelo app dentro da imagem** (`icons::render_key`, Segoe UI); o rótulo do aparelho fica desligado (`ShowTitle: false`). Isso permite cor por tecla: `color` (fundo), `icon_color`, `text_color`, `border`. Tamanho e cor padrão do texto vêm de `label` (tamanho × 2,4 px). Essas regras ficam só em `icons::Look::new`, a partir da `Appearance` (`Key::appearance` / `KeyFace::appearance`): o motor e a prévia do editor (`render_key` no `main.rs`) usam a mesma função, então não podem divergir.
- Tecla de dois estados: `toggle` (um `KeyFace`) alterna a cada toque; o estado vive só na memória do motor, por (nome da regra, tecla da pasta, número). Com uma ação `system`, a segunda face segue o estado real do Windows (ver abaixo).
- Ação "abrir" de um `.exe` escurece a tecla enquanto o app não roda (`Action::watched_process`; `watch: false` desliga). Explorer não conta; `wt.exe` vira `windowsterminal.exe`.
- Ícones de app (`icons::app_icon`, via `IShellItemImageFactory`) e de site (favicon do cache do Edge pela extensão, permissão `favicon`) são salvos como PNG em `%APPDATA%\D200Deck\icons`.
- Visor (`screen.rs`): `config.screen` e `rule.screen`; conteúdos desenhados pelo aparelho (`device_clock`, `device_stats`) ou pelo app (relógio, uso do PC com GPU via PDH, os dois juntos, agora tocando com capa via `GlobalSystemMediaTransportControlsSessionManager`, cronômetro, imagem, texto). O uso do PC é lido numa thread própria (`screen::watch_usage`, a cada 2 s), aberta na primeira vez que um visor o mostra: abrir os contadores de GPU leva mais de 1 s (medido em 1,3 s em 2026-10-11) e cada leitura uns 10 ms, que a thread do aparelho esperaria; antes, todo mundo pagava esse segundo ao abrir o app. Redesenha só quando a assinatura muda, e então manda ao aparelho só o visor (`send_visor`), sem refazer as teclas; esse envio, a cada 1 ou 2 s com relógio ou uso do PC, fica no log só em nível debug. O campo antigo `window` ainda é lido: o `Config::load` preenche o `screen` a partir dele, e uma config nova já nasce com `screen` (`fill_screen`), então a janela sempre recebe um. O `Config::default()` continua com `screen: None`: os campos que faltam no JSON vêm dele (`#[serde(default)]`), e um `screen` preenchido ali tomaria o lugar do que o `window` antigo diz.
- Toque e segurar no visor (`runtime/visor.rs`): `screen.action` roda no toque; `screen.hold` roda ao segurar 700 ms, ainda com o dedo no visor, e é uma ação (`action`) ou uma sequência de conteúdos (`cycle`, avança um a cada vez e volta ao principal). O passo da sequência fica na memória, por regra. Sem `hold`, segurar conta como toque. No cronômetro, toque inicia/pausa e dois toques em até 450 ms zeram.
- `cargo run -p deck-engine --bin try-screen -- <pasta>` desenha exemplos de visor e de teclas em PNG para conferir.
- **Mais ícones** (`iconify.rs`; janela `IconifyBrowser.svelte`, aberta pelo "Mais ícones…" do seletor): as coleções do Iconify, a fonte do Icônes. A lista vem de `api.iconify.design/collections` e fica 7 dias em `%APPDATA%\D200Deck\iconify`. Uma coleção inteira vem do pacote npm `@iconify-json/<prefixo>` pelo jsDelivr na primeira vez que é aberta e fica em `iconify\sets`. O motor guarda até 3 em memória, e a janela pede páginas de 150 com o filtro feito no Rust, porque coleções de emoji têm dezenas de MB. A busca em todas usa a API (`/search`), às vezes lenta. Os nomes passam por `iconify::parse_id` antes de virar caminho ou endereço.
- **Prévias pelo motor, nunca `<img>` do Iconify:** o Cloudflare do `api.iconify.design` responde 429 (erro 1015, por alguns minutos) a quem pede muitos SVGs avulsos (`/<prefixo>/<nome>.svg`), e a primeira versão da janela fazia isso a cada busca. Resultados da busca e amostras da lista vêm como texto SVG de `iconify::lookup`: um pedido `/<prefixo>.json?icons=a,b` por coleção (uma busca toca de 40 a 60), 6 ao mesmo tempo, e cada ícone uma vez por execução. As amostras são pedidas quando a coleção aparece na lista e ficam em `iconify\samples.json`.
- A busca devolve aliases (`mdi:category` é o `mdi:shape`), às vezes girados ou espelhados. `parse_set` resolve os aliases como o `iconToSVG` do Iconify; eles e os ícones ocultos são achados pelo nome (`Set::get`), mas não aparecem na grade da coleção.
- O ícone escolhido vira `icons/<prefixo>-<nome>.svg`, e o D200 não precisa de internet. O motor desenha SVG no quadrado dos glifos (100 px na tecla, 140 px no visor), trocando `currentColor` pela cor do ícone; os coloridos mantêm as cores. Todo SVG passa por `draw::svg_options`: um `<image>` com `data:` vale, mas um que aponte para arquivo ou endereço é ignorado (o usvg leria o arquivo ao interpretar, e um caminho de rede faz o Windows mandar as credenciais ao servidor). Pelo mesmo motivo, `icons::local_file` recusa caminhos de rede (`\\servidor\…`) para imagens de tecla e de visor antes de abrir qualquer coisa. O resvg é compilado sem `raster-images`: PNG dentro de SVG não é desenhado. A janela só mostra `data:` URIs, e o `img-src` da CSP não libera nenhum endereço de fora. `cargo run -p deck-engine --bin try-iconify -- <pasta> sets|icons|search|samples|save` testa tudo numa pasta qualquer.

## Ajustes do Windows e pastas
- Ação `{ "type": "system", "setting", "set", "value" }` (`system.rs`). Ligar/desligar (`set`: `toggle` padrão, `on`, `off`): `bluetooth`, `wifi` (`Windows.Devices.Radios`), `microphone` e `sound` (mudo no `IAudioEndpointVolume` do dispositivo padrão; o microfone também no de comunicações), `dark_theme` (registro `Personalize` + `WM_SETTINGCHANGE`), `keep_awake` (requisição de energia, solta quando o app fecha). Escolher (`value`): `audio_output` (nome do dispositivo), `projection` (`internal`/`clone`/`extend`/`external`, `SetDisplayConfig`), `power_mode` (`efficiency`/`balanced`/`performance`). Uma vez: `sleep`, `monitor_off`, `empty_recycle_bin`.
- APIs não documentadas: `IPolicyConfig` (trocar a saída de áudio, a mesma do EarTrumpet) e `PowerSetActiveOverlayScheme`/`PowerGetEffectiveOverlayScheme` (carregadas na hora; o modo de energia só vale com o plano Equilibrado).
- **Estado real na tecla:** o motor lê `system::state` a cada 1 s (a cada 200 ms por 3 s depois de um toque) só para os ajustes que alguma tecla visível ou de pasta usa (`Action::watched_setting`). Desligado (ou outra opção em uso) mostra a segunda face; sem segunda face, a tecla escurece. Ajuste que o PC não tem (sem Bluetooth, saída desligada) escurece. Nesse caso o toque não alterna a memória.
- `system::state` roda na thread do motor, que entra no MTA na primeira chamada; os rádios ficam em cache. Ler todos os ajustes leva uns 7 ms (32 ms na primeira vez; `try-system -- state` mede), então ele fica ali: a lista de processos (~5 ms por segundo), o visor (2 a 5 ms) e 13 teclas (~26 ms) também são baratos.
- O motor usa o mesmo crate `windows` que o Tauri (0.62), compilado uma vez só. Nessa versão, esperar uma operação assíncrona do WinRT é `.join()` (era `.get()`), e o erro do último `GetLastError` é `Error::from_thread()` (era `from_win32()`).
- Pasta: `"folder": { "keys": { "2": … }, "stay": false }` numa tecla, no lugar de `action`/`toggle`. Aberta, ela toma o lugar de todas as teclas (`rules::resolve_folder`); a tecla 1 é sempre "Voltar" (`config::BACK_KEY`, `Key::back`, espelhado em `types.ts`), então a pasta usa as teclas 2 a 13. Usar uma tecla com ação fecha a pasta (a menos que `stay`), tecla vazia não. Fecha sozinha após 30 s sem toque, ao reconectar o aparelho ou se ela sumir da config. Não há pasta dentro de pasta. As teclas de uma pasta de regra agem como teclas da regra (`front`).
- Uma pasta aberta fica até ser fechada, mesmo que a regra dela deixe de valer; ela é achada de novo pelo nome da regra a cada recarga da config.
- `cargo run -p deck-engine --bin try-system -- state` lê todos os ajustes; `-- set <ajuste> [toggle|on|off] [valor]` aplica um (muda o PC de verdade); `-- outputs` lista as saídas de áudio.

## Versões e atualizações
- A `main` só muda por PR: o ruleset "Proteger a main" exige PR (0 aprovações, quem trabalha sozinho não aprova o próprio), bloqueia push forçado e exclusão, não tem exceções e exige o job "Testes" do `.github/workflows/ci.yml` (testes, build da interface, `cargo check` do app e tipos, em Windows). O CI roda em todo PR e de novo depois de cada merge na `main`; só a `main` grava o cache do Rust (`save-if`), de onde todo PR parte (o cache de um PR não pode ser lido por outro, e cada um compilava do zero). A branch é apagada no merge. Varredura de segredos com bloqueio no push e alertas do Dependabot estão ligados. O ruleset "Proteger tags de versão" deixa só administradores do repositório criarem, mudarem ou apagarem tags `v*`.
- Nos workflows: actions de terceiros fixadas por SHA com a versão no comentário (`@<sha> # v4.4.0`), que o Dependabot atualiza num PR por semana (`.github/dependabot.yml`, só actions; cargo e npm têm só os alertas). O `ci.yml` só lê o código (`permissions: contents: read`). Valor de `${{ }}` que vem de fora (nome da tag, título de PR) entra num `run:` só por variável de ambiente (`env: TAG: ${{ github.ref_name }}` e `$env:TAG`), nunca no texto do script: um nome de ref pode ter aspas e `$(…)`, que rodariam no job da chave de assinatura.
- A versão fica em três lugares que precisam bater: `Cargo.toml` (raiz, `workspace.package`), `app/src-tauri/tauri.conf.json` e `app/package.json` (`npm version X.Y.Z --no-git-tag-version` atualiza o `package-lock.json` junto). A extensão do Edge tem a versão dela.
- Notas de versão: ficam no `CHANGELOG.md`, uma seção por versão (`## X.Y.Z`), escrita no PR que sobe a versão. `.github/scripts/changelog-section.ps1 -Version X.Y.Z` imprime a seção, ou falha se ela faltar ou estiver vazia. O "Testes" de todo PR exige a seção da versão atual do `tauri.conf.json`. O script é UTF-8 com BOM, para o Windows PowerShell 5.1 ler os acentos.
- Release: subir a versão e escrever as notas num PR → merge → `git tag vX.Y.Z` na `main` e `git push origin vX.Y.Z`. O `.github/workflows/release.yml` (Windows) confere a tag contra as três versões, monta as notas (a seção do `CHANGELOG.md` mais um rodapé sobre o instalador), gera o instalador assinado e cria o release como **rascunho**, com as notas no texto e no `latest.json`. Ele não roda os testes (seriam uma segunda compilação, em debug): quem garante o commit é o CI, no PR e depois do merge, então a tag só é criada depois de o "Testes" da `main` passar naquele commit (`gh run list --workflow ci.yml --branch main --commit <sha>`). Publicar o rascunho: só então os apps instalados enxergam a versão nova. Rodar o workflow à mão só gera o instalador como artefato.
- Atualização no app (`app/src-tauri/src/update.rs`, `tauri-plugin-updater`): procura 20 s depois de abrir e a cada 6 h em `https://github.com/argus-cs/d200-deck/releases/latest/download/latest.json` (por isso o repositório é público). Achou: aviso no topo da janela e "Atualizar para X e reiniciar" na bandeja; só instala quando a pessoa manda. No Windows o instalador (modo `passive`) fecha o app e abre de novo com os mesmos argumentos. Um download por vez (`Updates::installing`): enquanto o instalador baixa, a bandeja mostra "Baixando a versão X…" desativado, a janela mostra o progresso (também se a bandeja começou ou se a janela for reaberta), a busca periódica não mexe em nada e outro pedido de instalação só devolve `Ok`. Esse outro pedido acontece mesmo sem clique duplo: o IPC do Tauri reenvia por `postMessage` um comando cujo `fetch` falhou, e recarregar a janela no meio do `install_update` conta como falha. Para testar sem instalar nada: `npx tauri dev --config <json>` com uma `version` menor e `plugins.updater.endpoints` apontando para um servidor local (o `http://` vale em debug) que sirva um `latest.json` com assinatura inválida; o plugin baixa tudo e só então confere a assinatura.
- **Chave de assinatura:** a privada fica em `%USERPROFILE%\.tauri\d200-deck.key` (senha em `d200-deck.password`) e nos secrets `TAURI_SIGNING_PRIVATE_KEY` e `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` do environment `release` do GitHub, que só tags `v*` e a `main` podem usar (o job do `release.yml` declara `environment: release`; para trocar: `gh secret set <nome> --env release < arquivo`); a pública está em `tauri.conf.json` (`plugins.updater.pubkey`). **Sem a privada, os apps instalados não aceitam mais atualizações**: manter cópia fora deste PC. Build local assinado: `TAURI_SIGNING_PRIVATE_KEY=<caminho> TAURI_SIGNING_PRIVATE_KEY_PASSWORD=<senha> npx tauri build`.
- O `generate_context!` precisa do crate `serde_json` no app quando o `tauri.conf.json` tem `plugins`.
- Dependências usadas por mais de um crate ficam em `[workspace.dependencies]` no `Cargo.toml` da raiz (os crates herdam com `workspace = true` e só acrescentam features). O `[profile.release]` usa `lto` e `codegen-units = 1` (executável menor, compilação mais longa) e não usa `panic = "abort"`: um panic numa thread de ação não pode derrubar o app.

## Interface (depois da Fase 5)
- Janela sem moldura (`decorations(false)`), barra de título própria com `data-tauri-drag-region`; posição/tamanho lembrados por `tauri-plugin-window-state`.
- `disable_drag_drop_handler()` é necessário para o arrastar e soltar do HTML funcionar no Windows.
- Tema claro/escuro por `prefers-color-scheme` (tokens em `app.css`); o D200 virtual é sempre escuro (tokens `--device-*`).
- Classes que os editores compartilham (`.field`, `.name`, `.notice`, `.ellipsis`, `.small-btn`, `.icon-btn`, `.segmented`) ficam no fim do `app.css`, e o componente só define o que difere (a regra com escopo vence a global). Antes de mover outra para lá: todo componente que usa a classe precisa já defini-la, senão ganha estilo novo; e a global de mesma especificidade que outra (`.small-btn` vem sempre com `.secondary`) precisa vir depois dela no arquivo. Helpers do frontend: `SearchBox.svelte` (busca com lupa), `storage.ts` (`stored`/`storedJson`/`store`: localStorage que falha em silêncio), `list.ts` (`moveItem`) e `otherApps()` no `api.ts` (apps abertos menos o próprio D200 Deck).
- Desfazer/refazer na `ConfigEditing` (pilha de snapshots da config, agrupando edições a menos de 800 ms; só a mudança que o próprio desfazer fez fica fora do histórico, e a edição seguinte sempre entra). Nenhum componente grava na config dentro de um `$effect`: vira uma edição que ninguém fez, é salva, e briga com o desfazer (o editor do visor preenchia o `screen` assim e prendia o histórico); o `App.svelte` só monta a `TitleBar` (barra de título, salvar, desfazer, pausar, botões da janela), os `Banners` (erro da config, mudança não salva, atualização, simulação), a `RuleNav` (navegação e regras com arrastar) e a página escolhida (`View` em `types.ts`).
- O painel da tecla escolhida é recriado a cada tecla (`{#key}` no `LayerEditor`): busca, lista aberta e erro pertencem à tecla em que foram feitos. Os diálogos de arquivo (`pick` no `main.rs`) têm a janela que pediu como dona (`set_parent`): ficam na frente dela e a travam até fechar; sem dona, o diálogo podia sumir atrás da janela com os editores ainda clicáveis. Escolhas que chegam depois do clique (ícone de app ou de site, e o ícone tirado de um `.exe`, que vem depois de o diálogo fechar) vão para a face em que foram pedidas: o `IconPicker` guarda o `onchange` no clique, e o `KeyEditor`/`ScreenEditor` passam um amarrado à face (`setIcon(key)`, `setImage(content)`). Ler a tecla só na chegada gravava o ícone na tecla que estivesse aberta.
- Pastas no editor: duplo clique numa tecla de pasta (ou "Editar a pasta" no `KeyEditor`) troca a grade do `LayerEditor` pelas teclas da pasta, com "Voltar" fixo na 1 e o visor travado. Escolher um ajuste do Windows sugere texto, ícone e segunda face (`settingLook`), sem apagar o que a pessoa já escolheu.

## Regras de site (Fase 3)
- `"when": { "site": "youtube.com" }` casa o domínio e os subdomínios; com `/` ou `*` vira curinga sobre "domínio/caminho" (`github.com/*/pulls`), valendo também para o que estiver abaixo. Esquema, `www.`, porta, query e fragmento são ignorados.
- Foco = Edge na frente **e** o site na aba selecionada da última janela do Edge usada. Aberto = qualquer aba do site.
- `front` numa tecla de site: a extensão seleciona a aba e foca a janela dela, o motor traz o Edge para a frente e executa a ação. Depois volta para a aba anterior (se o Edge já estava na frente) ou devolve o foco ao app anterior. Sem nenhuma aba do site aberta (uma pasta da regra continua aberta depois que a regra deixa de valer), a ação **não** roda e a janela mostra o erro: rodar mesmo assim digitaria o texto ou o atalho no app que estivesse na frente.
- Abas InPrivate não são vistas (a extensão não roda nelas, a menos que seja liberada).
- Quando a extensão se desconecta, as regras de site deixam de valer.

## Comandos
O Rust fica em `%USERPROFILE%\.cargo\bin`, que pode não estar no PATH do shell.
```
cargo test -p d200
cargo run -p d200 --bin probe -- list
cargo run -p d200 --bin probe -- test
cargo run -p deck-engine --bin deckd
cd app && npm install && npx tauri dev          # app com recarga do frontend
cd app && npx tauri build --debug --no-bundle   # target/debug/d200-deck.exe
cd app && npm run check                         # tipos do frontend
```
O app e o `deckd` não podem rodar juntos: os dois querem o aparelho e a porta 47820.
Feche o Ulanzi Studio (`UlanziDeck.exe`) antes de falar com o aparelho.

## Protocolo (resumo)
- Interface: usage page `0x000C` (consumer control, `MI_00` no Windows).
- Pacotes de 1024 bytes: `7C 7C` + comando (u16 big-endian) + tamanho total (u32 little-endian) + 1016 bytes; payloads maiores seguem em pacotes crus de 1024.
- No Windows, cada write leva o byte de report ID `00` na frente (1025 bytes).
- Layout: zip com `dummy.txt`, `Images/*.png` (196×196), `manifest.json` (chaves `"col_row"`) e `sentinel.txt`. Nenhum pacote de continuação pode começar com `0x00` ou `0x7C`.
- 14 posições: 13 teclas + o visor largo (índice 13).

### Validado no Windows (Fase 0, 2026-10-07)
- O report descriptor da interface 0 tem entrada e saída de 1024 bytes e nenhum report ID: o prefixo `00` nos writes é obrigatório.
- Layout completo (`0x0001`) e atualização parcial (`0x000D`) funcionam; a parcial muda só as teclas do manifest e mantém as outras.
- Eventos de tecla (`0x0101`) chegam com apertar e soltar; índices 0–12 são as teclas e 13 é o visor.
- O visor mostra a imagem da posição 13 no modo `Background`, mas não mostra o texto.
- Tocar no visor troca o modo dele no próprio aparelho; o `state` do evento segue a sequência `100 → 1 → 200 → 201 → 202 → 203 → 0 → 2`. O app precisa respeitar essa troca ou reimpor o modo escolhido.
- Sem keep-alive (`0x0006`), o aparelho entra em proteção de tela. Ao voltar o keep-alive ele acorda com o layout que já tinha: não é preciso reenviar o layout.
- A proteção de tela vem da falta do PC, não de inatividade: com keep-alive a cada 5 s o aparelho ficou acordado mais de 4 minutos sem nenhum toque.
- Dois processos podem abrir o aparelho ao mesmo tempo no Windows.
- **O aparelho guarda as imagens em cache pelo nome do arquivo no zip.** Nome repetido (mesmo entre execuções) mostra a imagem antiga ou nada. Por isso os nomes levam um contador que começa no relógio (`device.rs::next_nonce`).
- O visor estica a imagem que recebe para o painel; a proporção medida é **458×196** (`screen::WIDTH/HEIGHT`). `probe screen-test <w> <h> --window image` manda um padrão de teste.

Referências: redphx/strmdck (MIT) e glmagalhaes.mail/rs-ulanzi-d-200-linux (GitLab).

## Regras
- Não atualizar o firmware pelo Ulanzi Studio sem retestar o protocolo.
- Atalhos simulados não chegam a apps rodando como administrador.
- Ação "abrir": nomes sem pasta (`wt.exe`, `notepad.exe`) são procurados no PATH antes do `ShellExecuteExW` (`actions::find_in_path`). Passando só o nome, o Windows consulta o registro App Paths, onde a Store aponta para o `.exe` dentro de `WindowsApps`; aberto por ali, o app da Store nasce fora do pacote (o Terminal não abre, o Bloco de notas acusa DLL faltando). O `SEE_MASK_NOASYNC` também é necessário, porque a ação roda numa thread que termina logo.
- `cargo run -p deck-engine --bin try-open -- <alvo>` testa a ação "abrir" isolada.
